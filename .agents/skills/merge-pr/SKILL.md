# $merge-pr — Merge a PR and clean up

**IMPORTANT:** Before starting, tell the user "I'm executing `$merge-pr <PR#>`" and create a todo list with the phases below.

## Harness compatibility

Follow "Agent capabilities" in `AGENTS.md`: use supported tools or a conversation plan/checklist when a native capability is unavailable. Preserve every explicit approval gate below. Resolve repository paths from the active worktree root.

## Usage

```text
$merge-pr <PR#>
$merge-pr <PR#> <PR#> …
```

`<PR#>` is the pull request number. Several numbers, in any order, select the multi-PR mode below: it infers the order, accepts PRs stacked on another PR of the request, and gates the whole stack once.

## Golden rules

- **Never merge without explicit user go-ahead.** An explicit authorization in the current session applies only to the actions and scope it names; do not ask again for an action it already covers. A request that names several PR numbers to `$merge-pr` is that go-ahead for those PRs: it authorizes everything the multi-PR mode needs for them (choosing the order, retargeting stacked PRs to `main`, force-pushing with a lease against the recorded head, posting the gate status and the squash merges), and the skill does not ask again.
- **Never** attribute authorship or co-authorship to any AI model, assistant, agent, or harness in PR titles, descriptions, comments, or merge/squash commit messages. Inspect the final merge message and omit AI `Co-Authored-By` trailers, signatures, and “generated by/with” footers. Preserve legitimate human attribution.
- **Never merge a PR whose head commit lacks a passing local gate, or whose GitHub check failed.** Report what is missing or failed and stop.
- **Never remove a worktree with uncommitted or unpushed state** unless the user overrides.
- **Never change the main clone's checkout.** Another session may be working there. No `checkout`, `switch`, `pull`, `merge`, `rebase`, `reset` or `stash` in `MAIN`, and no merge command that does one for you. In `MAIN` the skill only fetches, reads, removes the PR's worktree and deletes the PR's branch.
- **Derive the gh user from this clone's `remote.origin.url`** — never hardcode.
- **Name the directory of every command.** `MAIN` is the first `worktree` entry of `git worktree list --porcelain`; the PR's worktree is the entry on its branch. Never rely on an earlier `cd`, and run path-sensitive commands one at a time.
- Set the shell tool's working directory to the directory for each command.

## Universal gh-user detection

Same snippet as `$work-issue`. Run it before every `gh` call.

```bash
origin_url=$(git config --get remote.origin.url)
expected_owner=$(printf '%s\n' "$origin_url" | sed -E 's|.*[:/]([^/]+)/[^/]+$|\1|')
gh auth switch --hostname github.com --user "$expected_owner" || {
  echo "Cannot select the account for this origin; stop and confirm the login."
  exit 1
}
```

This repository and personal forks use the origin owner as the login. If the owner is an organization or the switch fails, stop and confirm the intended account; never infer it from the first account printed by `gh auth status` or attempt non-interactive authentication.

## Step 1: Preflight

- Run the gh-user detection.
- Fetch PR metadata:

  ```bash
  gh pr view <PR#> --json number,title,state,mergeable,statusCheckRollup,headRefName,headRefOid,baseRefName,url
  ```

- Report to the user: PR number, title, base branch, head branch, state, mergeable status.
- If `state` is `MERGED`, the merge already happened: skip to Step 5 to finish the cleanup. If it is `CLOSED`, stop — nothing to do.
- Locate the local worktree: `git worktree list --porcelain` and match on branch name. This finds worktrees under `~/.wt/<repo>/` and older sibling ones alike.

## Step 2: Freshness check

- For a coordinated issue, inspect its reservation and arrange with its supervisor for the worker to stop. Confirm it cannot still modify the worktree before checking cleanliness, and keep it stopped through merge and cleanup. A stale heartbeat alone is insufficient. Do this before Step 4 so no worker writes to a branch that is being merged.
- Run the rest of Steps 2 and 3 in the PR's worktree.
- Check for uncommitted or unpushed state **now**, before the merge. Work left only in the worktree would not reach the merge, and Step 5 removes the worktree:

  ```bash
  git status --porcelain        # must be empty
  git log --oneline @{u}..HEAD  # must be empty
  ```

  If either is non-empty, stop and ask the user. Commit and push first, or get an explicit override.
- `git fetch origin`.
- Check whether the PR branch is rebased on the latest `origin/<baseRefName>`:

  ```bash
  git log --oneline origin/<baseRefName>..HEAD    # commits ahead of base
  git log --oneline HEAD..origin/<baseRefName>    # commits on base not in PR
  ```

- If base has advanced:
  1. Offer `git rebase origin/<baseRefName>`.
  2. Resolve conflicts (surface each to the user; do not auto-resolve non-trivial ones).
  3. Re-run the required checks after rebasing, including `./scripts/gate.sh` on the rebased head, and show the exact `git push --force-with-lease` command. Obtain explicit approval for this push unless the user already authorized it in this session. Approval to rebase or merge does not authorize a push.
  4. Re-read the PR: the rebased head has a new SHA, so Step 3 checks its own gate marker.

## Step 3: Gate check

The merge gate is the local gate (`./scripts/gate.sh`, see `docs/local-gate.md`), not GitHub CI. A squash merge lands the head commit's tree, and Step 2 made sure that head contains the latest base.

- The head SHA is `headRefOid`. When a local worktree exists, its `HEAD` must equal it.
- The gate passed when either holds:
  - The marker `$(git rev-parse --path-format=absolute --git-common-dir)/gitbox-gate/<headRefOid>` exists with `status=pass`.
  - The commit has a successful `local-gate` status: `gh api repos/<owner>/<repo>/commits/<headRefOid>/statuses --jq '.[] | select(.context=="local-gate") | .state'`.
- `status=partial` (a lane was skipped): report the skipped lanes and stop unless the user explicitly accepts the partial gate for this merge. One partial needs no acceptance: the marker has `skipped=remote-it` and `auto_skip=remote-it` (written by `./scripts/gate.sh --auto`), and `bash scripts/gate-scope.sh origin/<baseRefName>` run in the PR's worktree prints `unaffected`. Then the diff touches nothing the remote-it lane compiles or tests; say so in the report. A `needed:` result or any other skipped lane stays a stop.
- No marker: offer to run `./scripts/gate.sh --auto` in the PR's worktree (clean tree, `HEAD` at `headRefOid`), then continue on a pass. After the push already happened, `./scripts/gate.sh --report` publishes the result.
- A PR from anyone else runs untrusted code on my machines through the gate. Review its diff first, and run the gate only with my explicit go-ahead, from a temporary worktree at `headRefOid`.
- A squash merge copies every branch commit's co-author trailers into `main`, and GitHub then lists their authors as contributors. Check the PR title, body and commit messages with the hooks' checker, from the repository root, and stop on any finding until the commits are reworded and the body is edited:

  ```bash
  gh pr view <PR#> --json title,body,commits \
    --jq '.title, .body, (.commits[] | .messageHeadline, .messageBody)' \
    | .githooks/ai-attribution.sh
  ```

- `statusCheckRollup` holds the informational GitHub check:
  - Any `FAILURE` / `CANCELLED` / `TIMED_OUT` blocks the merge: report it with its log URL (`gh run view`) and stop.
  - `IN_PROGRESS` / `QUEUED` does not block: say it is still running and continue.

## Step 4: Merge gate

- Show the exact merge commands. Execute them only with explicit current-session authorization for this merge and scope; if that authorization is missing or no longer applies, wait for it. The merge authorization covers deleting the PR's remote branch:

  ```bash
  gh pr merge <PR#> --squash
  git ls-remote --heads origin <headRefName>
  # only when ls-remote still prints the branch:
  gh api -X DELETE repos/<owner>/<repo>/git/refs/heads/<headRefName>
  ```

- Prefer `--squash` unless the repo convention says otherwise (scan `gh pr list --state merged --limit 5 --json mergeCommit` if unsure).
- Never add `--delete-branch`. When the current branch is the PR's head, `gh` then checks out the base branch and pulls it in that checkout, which can be `MAIN`. Without it, neither command touches a local checkout, whatever directory it runs in. The repository may delete merged branches itself, so `ls-remote` decides whether the API call is needed.

**Require explicit go-ahead** ("merge it", "go ahead", "ship it"). Honor an existing authorization for this merge without asking again. Approval to push or create a PR does not authorize merging it; approval tied to a particular SHA must still match the verified head.

## Step 5: Cleanup

After successful merge:

For a coordinated issue already merged externally, perform Step 2's worker-stop check before cleanup. After cleanup, confirm the PR merged and the linked issue is fully resolved; do not infer resolution from a `Closes` string alone. With current-session permission to update its work unit, follow `.agents/skills/wu-coordinate-tasks/protocol.md` to mark only the optional matching task checkbox, including when this invocation resumes after an external merge. Merge permission alone does not authorize the issue-body edit. Record pending work-unit updates when permission is absent, and retain the report for later reconciliation. Release a resolved issue's claim only after confirming no active worker or unfinished work remains; a partial PR leaves it reserved. An issue claim can be released after resolution while a journal entry preserves a pending work-unit update.

1. Leave the worktree: run the rest of the cleanup in `MAIN`. Note `MAIN`'s current branch with `git rev-parse --abbrev-ref HEAD`; this step never changes it.
2. Update the remote-tracking refs only: `git fetch origin`. It never touches `MAIN`'s branch, index or files.
3. Check what is left: `git worktree list` and `git branch --list <branch-name>`. If both are gone, skip to step 5.
4. Otherwise remove what is left. The worktree was checked clean in Step 2; if it changed since, stop and ask. Do not run `git worktree remove --force` without explicit instruction. When the PR's branch is checked out in `MAIN` itself, delete nothing: leave the branch in place and report it, because switching `MAIN` to another branch is the user's call.

   ```bash
   git worktree remove "<worktree-path>"
   git branch -D <branch-name>
   git worktree prune
   ```

5. Measure how far `MAIN` is behind, without updating it: `git rev-list --count main..origin/main`.
6. Report: PR merged, worktree removed, local branch deleted, and whether the remote branch was deleted or already gone. If the PR body says `Closes #N`, GitHub has closed issue `#<N>`; a `Refs #N` leaves it open. State that `MAIN`'s `main` is `<count>` commits behind `origin/main`, and show the update command for the user to run, without running it:
   - `MAIN` on `main`: `git -C "<MAIN>" pull --ff-only origin main`.
   - `MAIN` on another branch: `git -C "<MAIN>" fetch origin main:main`, which fast-forwards `main` without touching the checkout.
   - A count of `0`: say `main` is up to date and show no command.

## Multi-PR mode

Merging K PRs one by one gates K times, because each merge moves `main`, the next PR is rebased and its SHA changes. Multi-PR mode gates the whole stack once. It applies when the user gives several PR numbers in one request and every PR belongs to the origin repository. The typed order never matters, and the request itself authorizes every step below (see the golden rules).

1. **Preflight each PR** as in Step 1. Leave out, with the reason, any PR that is not `OPEN`, has a failed GitHub check, has a worktree with uncommitted or unpushed state, or whose `baseRefName` is neither `main` nor the `headRefName` of another PR of the request. Record every `headRefOid`, `headRefName`, `baseRefName` and the base SHA (`origin/main`) as the stack's inputs.
2. **Infer the order.**
   - A PR whose base is another PR's branch goes after that PR (a chain). Its own commits are `<base PR headRefOid>..<headRefOid>`; for a PR based on `main` they are `$(git merge-base origin/main <head>)..<head>`.
   - PRs whose order nothing fixes go by ascending number.
   - Report the chosen order and why in one line before stacking, for example "2 then 5: 5 is based on 2's branch".
3. **Stack in a scratch worktree** created from `origin/main`, never in `MAIN` or a PR's worktree. For each PR in order, `git cherry-pick` its own commits. A PR whose commits are already in the stack adds nothing and takes the current tip as its position. After each PR, note the stack commit as that PR's position. On a conflict, abort the cherry-pick and retry the stack with the conflicting PR placed before the PR it conflicts with, unless a chain forbids it; keep the first order that stacks cleanly. When no order avoids the conflict, the mode ends for that PR and everything after it: report it and fall back to the one-by-one flow for the rest.
4. **Gate the tip once**: run `./scripts/gate.sh --auto` in the scratch worktree at the tip. A failure ends the mode: report the lane log, remove the stack and fall back to the one-by-one flow, or fix and restart with fresh inputs.
5. **Publish each PR at its stack position**, in order:
   - when its base is another PR, retarget it first: `gh pr edit <PR#> --base main`;
   - push it with a lease against the head recorded in step 1: `git push --force-with-lease=<headRefName>:<recorded headRefOid> origin <position>:refs/heads/<headRefName>`.

   PR k's branch now holds PRs 1 to k, so a squash merge of it lands exactly the tested tree of that prefix. A rejected lease means the head moved: stop as in step 6. Post `./scripts/gate.sh --report` for the tip.
6. **Check the inputs did not move**, then merge in order with `gh pr merge <PR#> --squash`, one at a time. Before each merge re-read the PR: its `baseRefName` must be `main`, its `headRefOid` the position pushed in step 5, and `origin/main` the previous PR's merge commit (the base SHA for the first). Any difference ends the mode at that point: stop, report which PRs are merged, and gate the rest one by one.
7. **Clean up** each merged PR as in Step 5, and remove the scratch worktree.
8. **Report** the order and why, the gate result, each PR's merge commit, and every PR left out or falling back with its reason.

The single gate stays valid only while nothing changes under it. These invalidate it: a PR head that moved since the inputs were recorded (a new push by anyone), `main` that moved for any reason other than this stack's own merges, a conflict while stacking, a failed lane on the tip, and any merge that did not land as a squash of the pushed position. Never merge a PR in this mode on a gate that one of those invalidated.

Example: PR 2 targets `main` and PR 5 targets PR 2's branch. `$merge-pr 5 2` orders them 2 then 5, stacks 2's commits and then only 5's own, gates the tip once, pushes 2 at position 1, retargets 5 to `main` and pushes it at position 2, then merges 2 and 5.

## Behavior notes

- The skill is resumable — if the merge succeeded but cleanup failed, re-invoking it from the main clone will notice the PR is `MERGED` and skip to Step 5.
- If the worktree was already removed manually, skip its removal silently; still report how far `main` is behind.
- Never delete the `main` branch. Never run `gh pr merge` on a PR whose `baseRefName` is not the repo's default branch without confirming with the user first. In multi-PR mode the request is that confirmation for retargeting a stacked PR to `main`, and the merge still requires `baseRefName` to be `main`.
- Multi-PR mode still stops and falls back to one by one on an unusable PR, a conflict that no order avoids, a failed gate lane, or a PR head or `main` that moved under the single gate.
