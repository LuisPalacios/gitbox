# Referencia de pruebas

El inventario de pruebas y cómo funciona el harness de pruebas. Para los niveles de prueba, la preparación del fixture y las checklists, consulta [testing.md](testing.md).

## Inventario de pruebas

Los recuentos son funciones de prueba Go de nivel superior (no se cuentan los subtests de `t.Run` ni `TestMain`) y las llamadas `test(...)` de nivel superior en las suites del frontend. Actualizo los recuentos de Go con:

```bash
rg -c '^func Test\w*\(t \*testing\.T\)' -g '*_test.go' pkg cmd internal
```

El total actual es de 1040 pruebas Go (779 en `pkg/`, 259 en `cmd/gui/`, 2 en `internal/`) y 90 pruebas del frontend. Los recuentos incluyen las pruebas tras los tags `sshd_integration`, `remote_host` y `remote_smoke`. Los archivos solo de Windows (`*_windows_test.go`) se incluyen en los recuentos, pero solo se ejecutan en Windows.

Mantengo los targets fuzz separados de los recuentos `Test*` anteriores. `pkg/config/fuzz_test.go` compara conjuntos de source, repo, ruta de clon resuelta, tipo de credencial efectivo, indicador de contenedor y workspace después de `Parse` → `Marshal` → `Parse`; ambos parseos deben producir `CurrentVersion`. El corpus de semillas contiene el ejemplo `json/gitbox.jsonc` sin comentarios y los fixtures de migración v2, v3 y v4 existentes. El paquete externo `config_test` permite que la propiedad llame a `status.RepoPath` sin un ciclo de imports entre config y status.

`pkg/workspace/fuzz_test.go` pasa bytes arbitrarios a `stripJSONC`: no debe provocar un panic ni aumentar la entrada, y debe conservar el JSON válido byte por byte. Las semillas incluyen comentarios, comas finales, cadenas que parecen comentarios, escapes y entradas truncadas. Estas propiedades complementan las pruebas de ejemplos existentes, que comprueban resultados concretos de migración y eliminación de comentarios; conservo esas pruebas.

`pkg/status/fuzz_test.go` comprueba `FuzzRepoPath` dentro de un dominio explícito: dos raíces absolutas y rutas relativas seguras para source, ID y clones ordinarios. Los overrides vacíos y las rutas relativas anidadas son válidos; los segmentos padre, las barras inversas, NUL y las tildes iniciales quedan fuera del dominio de rutas relativas. El target comprueba que el resultado siga siendo absoluto y quede léxicamente dentro de la raíz predeterminada, de source o de repo seleccionada. Ramas separadas comprueban overrides absolutos de clone y un único `../` inicial seguido de una ruta relativa segura. Las semillas con raíces temporales nativas se ejecutan en todos los OS; el corpus versionado también incluye raíces POSIX y Windows.

`pkg/rpc/fuzz_test.go` pasa bytes arbitrarios a `ReadFrame` mediante `FuzzDecodeFrame`: no debe entrar en pánico, un cuerpo devuelto debe caber en el tope de 16 MiB, y lo que acepte debe sobrevivir sin cambios a `WriteFrame` y a una segunda lectura. Las semillas incluyen una trama válida, dos tramas seguidas, cabeceras extra, una longitud por encima del tope, un cuerpo corto, saltos de línea sin retorno de carro, un banner antes de la cabecera y una longitud duplicada.

Este límite pertenece a la prueba, no al validador de config. Las configs aceptadas todavía pueden contener raíces relativas, segmentos de recorrido o overrides `~name` no soportados. La propiedad no garantiza contención para esas entradas ni sigue enlaces simbólicos en disco.

## Cómo funciona el harness de pruebas

### Helpers de pruebas unitarias en `pkg/ops`

- `isolate` (`ops_test.go`) apunta `XDG_CONFIG_HOME`, `GIT_CONFIG_GLOBAL` y la carpeta SSH a un directorio temporal, define `GIT_CONFIG_NOSYSTEM`, vacía `GIT_TOKEN` y devuelve una config nueva cuya única raíz está en ese directorio.
- `makeClone` crea un repo git en la ruta de clon planificada de un repo de una source, con un origin dado.
- `gitRun` ejecuta git en una carpeta y hace fallar la prueba si hay error.

### Carga del fixture

`requireIntegration` en `pkg/ops/fixture_test.go` carga `test-gitbox.json` para la prueba de escenario:

1. Se salta en modo `-short` y falla con instrucciones de preparación cuando falta el archivo.
2. Parsea el archivo con `config.Parse`, que ignora las claves `_test` desconocidas.
3. Lee `_test.token` de cada cuenta en una pasada JSON raw aparte.
4. Define `GITBOX_TOKEN_<KEY>` para cada cuenta con token.
5. `rejectRealPaths` rechaza un `credential_ssh.ssh_folder` igual a `~/.ssh` y cualquier raíz de `global.roots` que sea el directorio de config de gitbox.
6. Apunta el SSH de git a la config SSH del fixture mediante `GIT_SSH_COMMAND`.

Después, el escenario define un `XDG_CONFIG_HOME` temporal, construye una config nueva cuya única raíz es un directorio temporal, y guarda y recarga la config tras cada paso, igual que la GUI persiste tras cada acción. `firstAccountWithRepos` elige la cuenta: la primera source, en orden de clave, con repos y un token. `t.TempDir()` borra los clones después.

### Modo de prueba

`GitboxApp --test-mode` usa `config.PrepareTestFixture()` en `pkg/config/testmode.go`. Busca `test-gitbox.json` subiendo desde el directorio actual, aplica las mismas comprobaciones de rutas, escribe una config descartable con `global.roots` sustituido por un único directorio temporal (vaciando cada `source.root` y `repo.root`), define `GIT_SSH_COMMAND` e inyecta los tokens del fixture como variables de entorno. Un fixture vacío con el indicador de nivel superior `_test.firstRun` abre el asistente de configuración. La GUI borra el directorio temporal al salir.

### Pruebas de concurrencia y de procesos

- Las pruebas de refresco y de sondeo en `cmd/gui` bloquean trabajo inyectado en canales para solapar disparadores sin un runtime de Wails, y usan servidores HTTP locales para comprobar la concurrencia limitada, los sondeos compartidos, los plazos y el estado upstream conservado tras errores o rotación de credenciales.
- Las pruebas de contexto de credenciales usan servidores de proveedor locales y un script de helper bloqueado para demostrar la cancelación.
- `credential_schedule_test.go` ejecuta Git real contra un repositorio bare temporal servido por HTTP en loopback. El helper del fixture avisa al empezar y después comunica que no está disponible o espera a la cancelación o al vencimiento del plazo. Compruebo el código de error, confirmo que los helpers bloqueados se detienen y verifico que las referencias y el árbol de trabajo quedan intactos.
- Las pruebas de mantenimiento en `pkg/git`, `pkg/heal` y `pkg/credential` usan config de git aislada, archivos include y worktrees enlazados, y cuentan los procesos git con `GIT_TRACE2_EVENT`: un clon SSH, token o GCM sin cambios lanza dos comandos git de solo lectura. Las pruebas de archivos de credenciales comprueban fechas de modificación sin cambios, lectores concurrentes, rotación, permisos y separación de cuentas. Las pruebas del escritor compartido también fuerzan un fallo de sustitución para verificar la conservación y la limpieza del archivo temporal. Los lectores de `GetToken` comparten el bloqueo del escritor; una prueba Windows confirma que un bloqueo externo de archivo puede rechazar la sustitución de forma segura sin recurrir a borrar primero. Las pruebas de auditoría de permisos usan archivos sintéticos; las pruebas Windows establecen DACL protegidas en lugar de asumir que un directorio temporal hereda permisos privados.
- `TestMain` en `pkg/terminals/detect_test.go` y `pkg/doctor/wsl_windows_test.go` convierte el binario de prueba en un `wsl.exe` falso que escribe un archivo centinela (`GITBOX_TEST_FAKE_WSL_SENTINEL`) cuando se ejecuta, así las pruebas demuestran que la detección de WSL nunca lo ejecuta.
- `.githooks/pre-push` elimina `GIT_DIR`, `GIT_WORK_TREE` y las demás variables que git exporta a los hooks, para que las propias llamadas a git de las pruebas apunten a sus repos temporales en lugar de a este repositorio.

## Referencia del mantenimiento del refresco

Medí el mantenimiento previo al fetch antes (`da83922`) y después de la reescritura con comparación previa sobre el mismo fixture aislado: 24 clones locales, una cuenta, ningún fetch de red, una pasada secuencial en caliente por plataforma, tipo de credencial y estado. En los casos con diferencias cambié ambos campos de identidad, origin y helper antes de cada pasada. El harness se ejecutó con Go 1.26.1; Windows usó Git 2.53.0.windows.1.

Los tiempos transcurridos cubren el bucle de mantenimiento completo en el proceso padre, incluida la creación de procesos, la ejecución de git, las operaciones de archivos y la sobrecarga del trazado. Los recuentos de procesos salen de los eventos de inicio de Trace2. Estas ejecuciones no separan el tiempo interno de git, no miden el pintado de la GUI ni estiman un refresco de red completo con ocho workers.

- **Tiempo interno de git** — una pasada aparte en Windows sobre 24 clones SSH sin cambios tardó 8.918 → 1.963 s en el proceso padre y 5.421 → 1.193 s de tiempo interno de git (sumado de los `exit.t_abs` de Trace2 de nivel superior). Los límites de producción siguen en diez segundos por petición y treinta por pasada, y estas cifras no predicen la latencia real del proveedor.

## Pruebas de sesión del modo remoto

Estas pruebas, en el mismo archivo y ejecutadas igual, comprueban el modo remoto contra un host real:

- `TestCutSSHMidSave`: se mata el `ssh` del cliente mientras `AddAccount` está en curso, 20 veces con retrasos distintos; el archivo del host siempre tiene las cuentas anteriores o esas más la nueva, y el lock de la config nunca sobrevive al servidor.
- `TestConfigChangedConflictOverSSH`: dos clientes, y por tanto dos servidores, leen la misma config del host; después de que uno añade una cuenta, la del otro falla con `config.changed`, y su reintento conserva las dos.
- `TestCutSSHMidClone`: el contenedor sirve un repositorio de prueba de 60 MB con `git daemon`, limitado con `tc netem` en el loopback, y se mata el `ssh` del cliente en cuanto el clon pasa del 30 %. Tras reconectar, el `gitbox.json` del host es el de antes del clon, no queda ningún proceso `git` del usuario de prueba, la carpeta no existe o `Reconcile` la señala como incompleta sin adoptarla, y el mismo clon funciona después.
- `TestTokenCanary` (`canary_integration_test.go`): el contenedor ejecuta una forja falsa (`test/fakeforge`), la API de Gitea y git por HTTP tras los tokens de un archivo. Se guarda un token aleatorio para una cuenta, y después el host clona, hace fetch y pull, configura un espejo pull, comprueba la credencial, cambia su tipo, ve rechazado GCM y la borra. El token cruza el cable al host una vez y acaba en un archivo `0600` en una carpeta `0700`; no está en ninguna respuesta, evento, error, log de conexión ni del servidor, línea de comandos del host (muestreada cada 50 ms con `ps`) ni línea de comandos del `ssh` de este lado, y no se ejecuta ningún `credential fill` (#242). El rechazo de GCM nombra el almacén del host: el llavero Secret Service en Linux, el llavero de macOS en un Mac.
- `TestSSHAccountOnRemote` (`ssh_account_integration_test.go`): un segundo contenedor es el proveedor git, cuyo usuario `git` tiene `git-shell` y es dueño de `org/small.git`. El host configura la clave de una cuenta SSH: `~/.ssh/gitbox-acct-sshkey` con modo `0600` en una carpeta `0700`, una sola entrada `Host gitbox-acct`, y la clave pública que recibe la ventana igual al archivo `.pub` del host. Cuando el proveedor conoce la clave, la conexión se verifica, `ssh -T gitbox-acct` en el host llega a `git-shell`, y un clon por SSH funciona con el alias como origen. La regeneración crea una clave nueva que el proveedor aún no conoce (#244).
- `TestPrivateKeyNeverOnWire` (`ssh_account_integration_test.go`): intercepta los dos sentidos de la sesión ssh durante una configuración, una verificación, un informe del agente y una regeneración; ninguna línea de ninguna de las dos claves privadas está en el cable, en el log de conexión ni en el del servidor, y las dos claves públicas están en las respuestas del host (#244).
- `TestAgentReport` (`ssh_account_integration_test.go`): un `ssh-agent` local con una clave propia, reenviado con `ForwardAgent` en el ssh config del cliente. El host informa del agente reenviado, lista la huella de esa clave y ningún comentario, no encuentra coincidencia, y ve que la entrada Host fija la clave de la cuenta, cuya huella coincide con la de `ssh-keygen -l` en el host; una conexión que no reenvía no informa de ningún agente (#244).
- `TestLatency300ms`: `tc netem` añade 300 ms a cada ida y vuelta entre cliente y host; el clon, el pull individual, Pull de todo y Fetch de todo terminan sin agotar el tiempo. Pull de todo actualiza el clon y correlaciona el evento de estado final con su pull. El progreso del clon llega agrupado, como mucho un evento por intervalo.

`TestIntegrationCallsEveryServedMethod` en `cmd/gui` mantiene `readOnlyCalls` igual a las lecturas servidas y `mutationCalls` igual a las mutaciones servidas.
