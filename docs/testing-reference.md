# Testing reference

The inventory of tests and how the test harness works. For test levels, the fixture setup and the checklists, see [testing.md](testing.md).

## Test inventory

Counts are top-level Go test functions (subtests from `t.Run` and `TestMain` are not counted) and top-level `test(...)` calls in the frontend suites. I refresh the Go counts with:

```bash
rg -c '^func Test\w*\(t \*testing\.T\)' -g '*_test.go' pkg cmd internal
```

The current total is 1078 Go tests (797 in `pkg/`, 279 in `cmd/gui/`, 2 in `internal/`) and 94 frontend tests. The counts include the tests behind the `sshd_integration`, `remote_host` and `remote_smoke` tags. Windows-only files (`*_windows_test.go`) are included in the counts but run only on Windows.

### Fuzz properties

I keep fuzz targets separate from the `Test*` counts above. `pkg/config/fuzz_test.go` compares sets of source, repo, resolved clone path, effective credential type, container flag and workspace after `Parse` → `Marshal` → `Parse`; both parses must yield `CurrentVersion`. The seed corpus contains the comment-free `json/gitbox.jsonc` example and the existing v2, v3 and v4 migration fixtures. The external `config_test` package lets the property call `status.RepoPath` without a config/status import cycle.

`pkg/workspace/fuzz_test.go` feeds arbitrary bytes to `stripJSONC`: it must not panic or grow the input, and valid JSON must remain byte-for-byte unchanged. Seeds include comments, trailing commas, comment-like strings, escapes and truncated input. These properties complement the existing example tests, which assert specific migration and stripping results; I retain those tests.

`pkg/status/fuzz_test.go` checks `FuzzRepoPath` within an explicit domain: two absolute roots and safe relative source, ID and ordinary clone paths. Empty overrides and nested relative paths are valid; parent segments, backslashes, NUL and leading tildes are outside the relative-path domain. The target checks that the result stays absolute and lexically inside the selected default, source or repo root. Separate branches check absolute clone overrides and one leading `../` followed by a safe relative path. Native temporary-root seeds run on every OS; the checked-in corpus also includes POSIX and Windows roots.

`pkg/rpc/fuzz_test.go` feeds arbitrary bytes to `ReadFrame` through `FuzzDecodeFrame`: it must not panic, a returned body must fit the 16 MiB cap, and whatever it accepts must survive `WriteFrame` and a second read unchanged. Seeds include a valid frame, two frames in a row, extra headers, a length over the cap, a short body, bare line feeds, a banner before the header and a duplicated length.

This boundary belongs to the test, not the config validator. Accepted configs can still contain relative roots, traversal components or unsupported `~name` overrides. The property does not guarantee containment for those inputs or follow symlinks on disk.

## How the test harness works

### Unit-test helpers in `pkg/ops`

- `isolate` (`ops_test.go`) points `XDG_CONFIG_HOME`, `GIT_CONFIG_GLOBAL` and the SSH folder at a temp directory, sets `GIT_CONFIG_NOSYSTEM`, clears `GIT_TOKEN`, and returns a fresh config whose only root is in that directory.
- `makeClone` creates a git repo at the planned clone path of a source repo, with a given origin.
- `gitRun` runs git in a folder and fails the test on error.

### Fixture loading

`requireIntegration` in `pkg/ops/fixture_test.go` loads `test-gitbox.json` for the scenario test:

1. It skips in `-short` mode and fails with setup instructions when the file is missing.
2. It parses the file with `config.Parse`, which ignores the unknown `_test` keys.
3. It reads `_test.token` from each account in a separate raw JSON pass.
4. It sets `GITBOX_TOKEN_<KEY>` for every account with a token.
5. `rejectRealPaths` refuses a `credential_ssh.ssh_folder` of `~/.ssh` and any root in `global.roots` that is the gitbox config directory.
6. It points git's SSH at the fixture's SSH config through `GIT_SSH_COMMAND`.

The scenario then sets a temp `XDG_CONFIG_HOME`, builds a fresh config whose only root is a temp directory, and saves and reloads the config after every step, the way the GUI persists after each action. `firstAccountWithRepos` picks the account: the first source, in key order, with repos and a token. `t.TempDir()` removes the clones afterwards.

### Test mode

`GitboxApp --test-mode` uses `config.PrepareTestFixture()` in `pkg/config/testmode.go`. It finds `test-gitbox.json` by walking up from the current directory, applies the same path checks, writes a throwaway config with `global.roots` replaced by one temp directory (clearing every `source.root` and `repo.root`), sets `GIT_SSH_COMMAND`, and injects the fixture tokens as environment variables. An empty fixture with the top-level `_test.firstRun` flag opens the setup wizard. The GUI removes the temp directory on exit.

### Concurrency and process tests

- Refresh and probe tests in `cmd/gui` block injected work on channels to overlap triggers without a Wails runtime, and use local HTTP servers to check bounded concurrency, shared probes, deadlines, and upstream state kept after errors or credential rotation.
- Credential context tests use local provider servers and a stalled helper script to prove cancellation.
- `credential_schedule_test.go` runs real Git against a temporary bare repository served over loopback HTTP. The fixture helper signals entry, then reports unavailability or waits for cancellation or a deadline. I check the error code, confirm blocked helpers stop and verify that refs and the working tree stay intact.
- Maintenance tests in `pkg/git`, `pkg/heal` and `pkg/credential` use isolated git config, include files and linked worktrees, and count git processes with `GIT_TRACE2_EVENT`: an unchanged SSH, token or GCM clone spawns two read-only git commands. Credential-file tests check unchanged modification times, concurrent readers, rotation, permissions and account separation. The shared-writer tests also force a replacement failure to verify preservation and temporary-file cleanup. `GetToken` readers share the writer lock; a Windows test confirms that an external file lock can reject replacement safely without a delete-first fallback. Permission-audit tests use synthetic files; Windows tests establish protected DACLs rather than assume a temporary directory inherits private permissions.
- `TestMain` in `pkg/terminals/detect_test.go` and `pkg/doctor/wsl_windows_test.go` turns the test binary into a fake `wsl.exe` that writes a sentinel file (`GITBOX_TEST_FAKE_WSL_SENTINEL`) when run, so the tests prove WSL detection never executes it.
- `.githooks/pre-push` unsets `GIT_DIR`, `GIT_WORK_TREE` and the other variables git exports to hooks, so the tests' own git calls target their temp repos instead of this repository.

## Refresh maintenance baseline

I measured pre-fetch maintenance before (`da83922`) and after the compare-first rewrite on the same isolated fixture: 24 local clones, one account, no network fetches, one warm sequential sweep per platform, credential type and state. In the drifted cases I changed both identity fields, origin and helper before each sweep. The harness ran on Go 1.26.1; Windows used Git 2.53.0.windows.1.

Elapsed times cover the whole maintenance loop in the parent process, including process creation, git execution, file operations and tracing overhead. Process counts come from Trace2 start events. These runs don't separate git-internal time, measure GUI paint, or estimate a full eight-worker network refresh.

| Platform | Clone state | Credential | Git processes before → after | Elapsed seconds before → after |
| --- | --- | --- | --- | --- |
| macOS arm64 | unchanged | SSH | 216 → 48 | 0.902 → 0.191 |
| macOS arm64 | unchanged | Token | 240 → 48 | 1.013 → 0.202 |
| macOS arm64 | unchanged | GCM | 192 → 48 | 0.923 → 0.278 |
| Windows amd64 | unchanged | SSH | 216 → 48 | 9.831 → 2.037 |
| Windows amd64 | unchanged | Token | 240 → 48 | 12.396 → 2.382 |
| Windows amd64 | unchanged | GCM | 192 → 48 | 9.386 → 2.202 |
| macOS arm64 | drifted | SSH | 288 → 264 | 1.311 → 1.216 |
| macOS arm64 | drifted | Token | 312 → 288 | 1.457 → 1.319 |
| macOS arm64 | drifted | GCM | 264 → 288 | 1.222 → 1.402 |
| Windows amd64 | drifted | SSH | 288 → 264 | 12.774 → 11.085 |
| Windows amd64 | drifted | Token | 312 → 288 | 13.576 → 12.089 |
| Windows amd64 | drifted | GCM | 264 → 288 | 11.105 → 13.073 |

GCM drift repair validates the effective config after writing, so its drifted case costs more than before. I keep that check so a fetch never runs with settings an include or worktree config overrides.

- **Git-internal time** — a separate Windows sweep of 24 unchanged SSH clones took 8.918 → 1.963 s in the parent process and 5.421 → 1.193 s of git-internal time (summed from top-level Trace2 `exit.t_abs`). The 3.497 → 0.770 s residual covers process startup, IPC and caller file operations; I don't attribute it to antivirus or `HideWindow` alone.
- **Probe scheduling** — native Windows amd64 runs on Go 1.27.0 with loopback HTTP servers: twelve upstreams shared by two sources made twelve requests, one credential lookup and at most four concurrent requests. With a 20 ms per-request timeout, twelve stalled requests finished in 61.34 ms; with a 20 ms overall budget, the sweep stopped after four requests in 20.57 ms. Production limits stay at ten seconds per request and thirty per sweep, and these numbers don't predict real provider latency.

## Remote mode bootstrap tests

`scripts/remote-it.sh` runs `pkg/remote/integration_test.go` on a Linux host with Docker; [testing.md](testing.md#remote-mode-tests) describes the setup. Each test gets a fresh `gitbox-sshd` container on an internal network, and installs the real server built with the `e2e_sentinel` tag. `scripts/remote-host-it.sh` runs the same file against a real host, such as a Mac (#245): the bootstrap tests below but `TestNoexecHome`, `TestBannerOverflow`, `TestUnknownHostFailsFast` and `TestFishLoginShell`, which need a container of their own, plus `TestTokenCanary`. Each test gets a folder of its own under the account's `~/.gitbox-it/` as its `server_dir`.

- `TestInstallNoInternet` — the container has no default route; install and handshake succeed, and the binary and its folder are 0700. A real host keeps its network, so there the test checks the modes only.
- `TestRejectCorruptBinary` — bytes flipped in the upload give `hash_mismatch`, no final file and no run.
- `TestRejectWrongHash` — a different pin gives `hash_mismatch` at the install's hash check, and `ran.log` does not grow.
- `TestRejectModifiedBetweenStarts` — one byte appended to the installed binary gives `hash_mismatch`, and the `ran.log` count does not change.
- `TestPreviousVersionInstalled` — an older build with a live marker survives garbage collection; with its marker back-dated 11 minutes, the next start removes it.
- `TestConcurrentInstall` — two clients install at once: one final binary with the right hash, two live markers, no temporary file; after one disconnects its marker is gone, the other stays, and a third start keeps the version.
- `TestInterruptedUpload` — `ssh` killed at half the upload leaves the temporary file and no final file; back-dated 2 hours, the next connect succeeds and removes it.
- `TestNoexecHome` — a `noexec` tmpfs home gives `noexec` with the `server_dir` hint, and `docker diff` shows nothing written outside the home.
- `TestNoisyBashrc` — 64 KiB on stdout and on stderr from `.bashrc`, or from `~/.zshenv` on a host whose login shell is zsh; both hash checks read the right value.
- `TestBannerOverflow` — 1 MiB plus one byte of banner gives `banner_overflow`.
- `TestStaleGCLock` — a lock 10 minutes old is broken, the client log and the server log file both record it, and the lock is released.
- `TestUnknownHostFailsFast` — an empty `known_hosts` gives `ssh_hostkey` in under 12 seconds and installs nothing.
- `TestFishLoginShell` — with fish as the login shell, probe, install and start succeed.
- `TestRemoteTerminalOverSSH` — the remote command of a terminal, through a real `ssh` into bash, fish and `sh` login shells (on a real host, its own login shell: zsh on a Mac), lands in each hostile folder, checked with the external `pwd` in both the program form and the login-shell form, and no injected command leaves a marker.

## Remote mode session tests

These tests, in the same file and run the same way, check remote mode against a real host:

- `TestReadsLeaveTheDomainUntouched`: the container's `gitbox.json` holds one account on a server it cannot reach, one clone with a bare origin, and an AI harness that detection marks missing. The test calls every served read over the real `ssh` transport, runs Fetch all and keeps the session open past the harness watcher's first pass. The server refuses `OpenAccountFolder`, a Backend method outside its list, with `unsupported`, the config's domain (all but `ai_harnesses`, which the watcher saves) is the same before and after, and the fetch repaired the clone's `.git/config` first.
- `TestMutationsOverSSH`: every served mutation of `mutationCalls`, config and repository ones, answers in order over a real session (those that need a provider fail with the domain's error, never `unsupported`), the host's `gitbox.json` parses after each step and keeps its own theme, and the end state holds what the sequence left.
- `TestCutSSHMidSave`: the client's `ssh` is killed while `AddAccount` is in flight, 20 times at different delays; the host's file always holds the old accounts or those plus the new one, and the config lock never outlives the server.
- `TestConfigChangedConflictOverSSH`: two clients in sessions without the daemon, so two servers, read the same host config; after one adds an account the other's add fails with `config.changed`, and its retry keeps both.
- `TestCutSSHMidClone`, in a session without the daemon: the container serves a 60 MB fixture repository with `git daemon`, slowed with `tc netem` on the loopback, and the client's `ssh` is killed once the clone passes 30 %. After a reconnect the host's `gitbox.json` is the one before the clone, no `git` process of the test user is left, the folder is gone or `Reconcile` reports it incomplete without adopting it, and the same clone then succeeds.
- `TestTokenCanary` (`canary_integration_test.go`): a fake forge (`test/fakeforge`) serves Gitea's API and Git over HTTP. The host stores one random token on an existing account, then clones, fetches, pulls, sets up a pull mirror and verifies that credential. It switches a separate account to a second token, refuses GCM and deletes both credentials. The test allows each token only in its designated client request parameter and active `0600` credential file in the `0700` directory. It checks for leaks in config, answers, events, errors, logs and process command lines. The GCM refusal names the host's credential store and starts no `credential fill`. It runs twice, in a session the host serves itself and in one through the daemon, whose `events.log` must not hold the token either (#247).
- `TestSSHAccountOnRemote` (`ssh_account_integration_test.go`): a second container is the git provider, whose `git` user has `git-shell` and owns `org/small.git`. The host sets up an SSH account's key: `~/.ssh/gitbox-acct-sshkey` in mode `0600` in a `0700` folder, one `Host gitbox-acct` entry, and the public key the window gets equal to the host's `.pub` file. Once the provider knows the key, the connection verifies, `ssh -T gitbox-acct` on the host reaches `git-shell`, and a clone over SSH works with the alias as its origin. The regenerate makes a new key the provider does not know yet (#244).
- `TestPrivateKeyNeverOnWire` (`ssh_account_integration_test.go`): taps on both directions of the ssh session through a setup, a verify, an agent report and a regenerate; no line of either private key is on the wire, in the connection log or in the server log, and both public keys are in the host's answers (#244).
- `TestAgentReport` (`ssh_account_integration_test.go`): a local `ssh-agent` with a key of its own, forwarded with `ForwardAgent` in the client's ssh config. The host reports the agent as forwarded, lists that key's fingerprint and no comment, finds no match, and sees that the Host entry pins the account's key, whose fingerprint matches the host's `ssh-keygen -l`; a connection that does not forward reports no agent (#244).
- `TestLatency300ms`: `tc netem` adds 300 ms to every round trip between client and host; clone, individual pull, Pull all and Fetch all complete without timing out. Pull all advances the clone and correlates the authoritative row status with its pull. Clone progress arrives coalesced, one event per interval at most.

`TestIntegrationCallsEveryServedMethod` in `cmd/gui` keeps `readOnlyCalls` equal to the served reads and `mutationCalls` to the served mutations.

## Remote mode daemon tests

`daemon_integration_test.go` runs the acceptance tests of the daemon (#247) the same way, with every session through `gitbox-server proxy`:

- `TestKillSSHDuringFetchAll`: 50 small repositories served by `git daemon` with 100 ms more per round trip; the client's `ssh` is killed after 15 `fetch:done` events. The daemon finishes the run, the client is connected again within 30 seconds with `remote.DefaultReconnect`, the `fetch:done` events from before the cut and from the resume cover every repository, and `GetAllStatus` equals what a fresh client reads.
- `TestResumeInFlightClone`: the 60 MB fixture at 40 Mbit/s; the client's `ssh` is killed past 30 %, and git keeps running on the host. After the reconnect, `CloneRepo` with the same request id returns the daemon's result, `clone:done` reports no error, and the trace2 files of the host's git (`trace2.eventTarget`) hold one `clone`.
- `TestPeriodicSyncWhileDisconnected`: `SetFleetSchedule("1m")`, which only the `e2e_sentinel` build accepts, then no client for three minutes: `events.log` holds at least two `fetch:alldone` runs, and a resume replays them.
- `TestNoZombieDaemons`: an old build with its daemon running is collected when a new session starts, with its daemon stopped first, and after the uninstall `pgrep -u test gitbox-server` finds nothing.
- `TestSocketPermissions`: `rpc.sock` belongs to the test user with mode 0600 in a 0700 folder; `testdata/sockprobe`, run as the `git` user, cannot reach it, and with every mode on the way opened on purpose it is closed by the daemon, which logs the uid 1001 and nothing the peer sent.
- `TestHeartbeatDeadLink`: `tc netem loss 100%` on the container's interface; the client declares the link dead within three missed pings and 15 seconds, the first attempt fails while the link is down, and the next one connects to the same daemon and resumes.
- `TestConfigChangedWithTheDaemon`: two clients reach one daemon and both adds succeed; after another process changes the host's `gitbox.json`, the next add fails with `config.changed` and its retry keeps every change.
